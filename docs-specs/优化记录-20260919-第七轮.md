## 一、个人数据与密钥泄露（最高优先级）

1. **公网下载包含全部真实个人数据**。`pack_public.py` 复用为私有云电脑副本设计的
   `DATA_KEEP`，把 `data/` 整份打进 `cloud_deploy_public.zip`，而 `download_site` 对外
   提供该文件下载：真实聊天记录（sessions.json / memory / state / story）、**23 张用户
   发来的照片**（uploads）、**21.7 MB 真人语音**（clone_ref，含 16.4 MB 纪录片素材）。
   语音属可识别个人的生物特征信息。构建日志只打印「密钥已置空」，完全看不出数据在包里。
   - 公网包不再携带任何 `data/`（`PUBLIC_DATA_KEEP = []`；解压后首次启动会自动建好空目录）。
   - 新增 `verify_public_package()` 出厂自检：包内出现 `data/`、`.env`、内部部署文档、
     或任何非空凭据字段 → **构建直接失败**，不留下可发布的包。三份公网脚本全部接入。
   - 实测重建：57 个文件 / 7.6 MB，`data/` 成员 0、凭据字段 0。
2. **脱敏从「枚举已知路径」改为「按叶子名」**。`SENSITIVE_PATHS` 只登记了 5 个 provider，
   而 `POST /api/config` 接受前端传入的任意 `cloud_provider` 并把 `api_key` 写进
   `cloud_providers.<新名>.api_key`；`local.api_key` 也从未在名单里。这类密钥会原样进包。
   现按叶子名（`api_key`/`access_token`/`token`/`secret`/`password`…）递归清空，
   精确匹配而非子串，`news.keyword` 不受影响。
3. **`/api/status` 明文回传 `local.api_key`**（由本轮新增的运行时冒烟实测抓到）。
   脱敏同样是逐字段手写，漏了 `local` 与 `voice.mimo`。服务绑 0.0.0.0 并经公网隧道暴露，
   该字段随每个登录会话的轮询传输。改为响应体统一走 `mask_credentials()`（与打包脱敏共用
   叶子名常量），并在深拷贝上操作以免污染 `load_config` 缓存。
4. 内部部署文档（`deploy/README_*`：私有仓库地址、webhook 端口、`git pull` + 重启拓扑）
   不再进入公网包。
5. **HEIC 转码解压炸弹**。`_heic_to_jpeg_bytes` 显式设 `DISABLE_SECURITY_LIMITS = True`
   放行 iPhone 元数据，等于关掉了 Pillow 的像素上限，而它处理的是公网可上传的文件。
   补 80 MP 像素闸门（覆盖 48 MP iPhone，挡住构造文件），超限返回 None 走原降级链。
6. **webhook 自动部署接收器**：`HTTPServer(("0.0.0.0", port))` 改绑 `127.0.0.1`
   （隧道本就按 127.0.0.1 回源，无需对全网卡开放「拉代码 + taskkill + 起服务」的执行入口）；
   口令比较改 `hmac.compare_digest`。
7. **登录 cookie 不再是口令本身**，改为 `HMAC(token, scope)`：截获 cookie 推不回口令，
   也不再存在一把 30 天有效、无法轮换的凭据。`Secure` 位改按 `X-Forwarded-Proto` 末跳判定
   （所有启动命令都没开 uvicorn `--proxy-headers`，`req.url.scheme` 在隧道下恒为 http，
   此前 Secure 永远设不上）；可信度推理复用 `_client_ip` 的「仅当直连对端是本机/内网才采信
   X-Forwarded-*」，抽出 `_behind_local_proxy()` 共用。
   > ⚠️ 升级后各端登录 cookie 失效，需在登录页重填一次访问口令。

## 二、数据正确性

8. **附件回收会删掉历史消息仍在用的图片**。`_scan_expired_uploads` 按 atime/mtime 超 7 天
   无条件删除，但附件被 sessions.json 无限期引用；浏览器/SW 命中缓存时不发请求、服务端
   atime 不刷新，Windows 的 atime 更新还受卷策略与 1 小时节流影响。
   **实测本机：`data/uploads` 23 个文件全部已超 7 天，其中 8 个仍被会话引用** —— 下一次
   6 小时周期的清理就会让它们永久 404。现只删「过期 **且** 无任何会话引用」的孤儿
   （整份文本正则匹配，覆盖正文里直贴的 `/uploads/...` 链接）；读不到会话存储时整轮跳过
   （无法证明无引用就宁可不删）；`att_inflight_*` 崩溃残留按 1 小时回收。
9. 上传中途失败不再回删已落盘的内容寻址文件：并发的另一端可能已去重命中并拿到该 URL，
   回删会造成对端历史消息 404；真孤儿由第 8 条的引用集回收。顺带修 `dest.exists()+stat()`
   的 TOCTOU。
10. **`PUT /api/sessions` 截断方向反了**。两端都以「最新在前」排序，`req.sessions[-500:]`
    保留的却是最旧 500 条 —— 超过 500 会话的用户，正在聊的和置顶的会话进不了合并、
    写盘时被丢弃，所有设备上一起消失。改为按 `updatedAt` 排序后取前 500，不依赖入参顺序。
11. **长期记忆会被静默清空**。`role_engine._safe_load` 把 `OSError` / `UnicodeDecodeError`
    也当作「文件损坏」直接写回空库；而本项目跑在云盘同步目录里，同步客户端与杀软的瞬时
    锁、跨进程 `os.replace` 期间的读取都会抛这两类异常，此时磁盘数据完好。现在只有
    `JSONDecodeError` 才重置，且重置前先落一份 `<name>.corrupt-<ts>` 副本。
12. **剧情战绩双计**。`if not self.save() or not self._save_calendar()` 走短路：
    `save()` 已把新战绩与 log 写进 state.json，`_save_calendar()` 失败时只回滚内存 →
    磁盘上 state 是「已记」、calendar 是「待宣布」，重启后同一场被再记一次。
    改为先写日历（没写成就等于什么都没提交）再写状态，失败走 `_rollback()` 把两份都回写。
13. **StoryManager 双实例**。`_get_story_manager()` 无锁，lifespan 的 `to_thread` 预热与
    首个聊天请求可同时看到 `None`，各建一个实例；实例内的 `RLock` 跨实例零互斥，
    两个 `state` 各写各的盘，后写者覆盖 → 剧情 flag/log 静默丢失。改双检锁。
14. **事件循环阻塞**：story 的记录/撤销（deepcopy 整季日历 + 两个 JSON 写盘 + Windows
    占用时 `time.sleep` 退避）与 `_collect_role_facts`（stat+读+解析 memory/state）都直接
    写在 `async def` 里，同步调用会冻住全场 SSE。全部 `asyncio.to_thread` 化。
15. `role_memories` 对 `{"importance": null}` 走 `float(None)` → 整个记忆管理页 500
    （聊天链路用 `_fnum` 反而正常，很难定位）。改用 `_safe_float` / `_safe_int`。
16. `_role_stores` 是文件里唯一没有上限的缓存，而 `role` 来自用户可控的 query 参数
    （`_sanitize_role` 只校验格式不校验是否为已配置角色）。补 FIFO 上限 64，与其它缓存一致。
17. **TTS 缓存对 mimo 永不失效**：`_voice_fingerprint` 只有 aliyun / minimax 两个分支，
    mimo 的 `model`/`voice`/`ref_audio`/`base_url` 全在子配置里、顶层 `voice.*` 读不到，
    指纹恒定 → 重新克隆音色后永远播旧声音。补 mimo 分支 + 把 `ref_audio` 的
    mtime/size 纳入失效判断；minimax 补 `api_schema`（官方与 GMI 是两套上游）；
    顶层 `voice.style` 也纳入指纹。
18. `PUT /api/sessions` 写盘抛 OSError 时把 `sessions.tmp`（可达数十 MB）留在盘上；
    现失败即回收并返回明确 500。
19. GMI TTS 的 `vol`/`pitch` 直接 `int(m.get(...))`，手改成 null / "1.5" 即 500；
    与官方协议路径用同一套钳制。
20. 视觉两个后端失败时零日志 —— 表现为「角色说看不到图」，运维无法区分 key 轮转 /
    不支持图片 / 读超时。补 warning（含 model）。

## 三、前端

21. **发消息会丢消息**：上传附件期间多端合并可能整体替换会话对象，而 `send` 仍写回 await
    之前抓到的旧引用 —— 气泡在屏上，`saveSessions` 序列化的是新数组，刷新后这条用户消息
    连同图片永久消失。合并后重新 `findSession` 取最新引用。
22. **删除旁白气泡只删 DOM 不删数据**：narration 是 assistant 条目的字段、不占 `hidx`，
    两条匹配分支都落空，切会话/刷新后旁白又回来。改为按字段清除并在任何分支后都重渲染。
23. **循环播放让多端同步永久停摆**：loop 下 `ended` 不触发、`state.playing` 不释放，
    `isSyncBusy()` 恒真 → 所有合并入口被挡，而对端看起来一切正常。循环播放只挡重渲染
    （传 `preserveScroll` + `keepAudio`），不挡数据合并。
24. 分叉合并重建会话时漏传 `role` → 2027 分支会话变成 `role:''`，在所有设备泄漏进
    普通角色会话列表（且因合并结果回传而固化）。
25. `editMessage` 只按会话判并发，缺 `send`/`regenerate` 那把全局门禁 → 能起第二条流，
    `chatAborter` 单槽被覆盖，旧流再也停不掉（白烧 180 s 超时且该会话 awaiting 一直挂着）。
26. ngrok 重启换域名后，`refreshStatus` 的 6 次重试封顶不再自试，"后端未连接"一直挂在
    界面上即使功能已恢复。`online` 与回前台时清零重试计数并重探。
27. SW 壳缓存 bump 到 `xiaoni-shell-v10`（SWR 策略下不 bump 要等用户第二次刷新才拿到新 app.js）。

### 启动脚本（.bat）—— 被实证的高危类
38. **全部 8 个 .bat 归一为 UTF-8（无 BOM）+ CRLF**，含非 ASCII 的一律补
    `chcp 65001 >nul`。原状态：`start.bat`/`setup.bat` 是 GBK、`start_deploy.bat`/
    `start_test_server.bat`/`_run_service_detached.bat` 是 **UTF-8 + 纯 LF**。
    这不是洁癖：本轮我改 `run_tests.bat` 时踩中同一类问题（LF + 嵌套 if/else 让 cmd
    解析器报 `else was unexpected at this time` 直接退出 255），而 `start_deploy.bat`
    正是「LF + 两个 else 块」。改完用无副作用探针（把 start/taskkill 换成 echo）实测
    `start_deploy.bat` 与 `start.bat` 解析通过、中文正常渲染。
39. `start_deploy.bat`：解释器缺失时 `errorlevel=9009` 同样 ≥1，被误判成「服务没在跑」，
    于是拿不存在的 python 去 start，最后还打印「自启完成」—— 任务计划静默失败。
    现在先校验解释器存在并支持 `AI_PERSONA_PY` / `AI_PERSONA_NGROK` / `AI_PERSONA_URL` 覆盖，
    ngrok 不存在时明确报「服务在跑但公网入口没起来」。
40. `start.bat`：双击第二次会再起一个 uvicorn，新进程必然崩在 8000 端口占用上，
    窗口里只剩一屏 traceback。现在先探健康、已在线就直接开浏览器并提示改用 restart。
41. `install_cloud.bat`：`Start-Process -RedirectStandardOutput data\service.log` 在
    全新解压（还没有 data/）时直接失败；补 mkdir。`deploy/webhook_autodeploy.py`
    的接收端口从 0.0.0.0 收窄到 127.0.0.1（见第 6 条）。
42. `requirements-tools.txt` 新建并进打包白名单：`pet_process.py` 需要的
    `av==18.0.0 / numpy==1.26.4 / onnxruntime==1.28.0` 此前任何清单都没有登记
    （实测只在 t2i-tts venv 里存在，换环境即 ModuleNotFoundError，且它在模块顶层
    import —— 连 `--help` 都跑不出来）。版本号按实测记录，并注明抠图模型不是 pip 依赖。

### 桌宠
43. **拖拽状态会永久卡死**。`setPointerCapture` 失败被吞掉，而 `pointerup`/`pointercancel`
    只挂在宠物元素上；宠物在拖到视口边缘时会被钳制在视口内而手指能继续移出元素，
    或系统手势（Home/切应用）抢走指针 —— 于是 `endDrag` 永不执行，`activePointerId`
    残留，`pointerdown` 首行的 latch 从此拒绝一切按下：**拖拽和长按菜单一起失效，
    直到刷新页面**，且宠物会一直跟着光标走。现在 window 上兜一层 + `lostpointercapture`
    + `e.isPrimary` + latch 自愈（`drag` 为 false 时重置并接受新指针），同时保留
    pointerId 比对，第二指的 pointerup 不会误结束第一指的拖拽。
44. **长按转拖拽后，下一次真实单击被凭空吃掉**：合成 click 在 `_suppressClickUntil`
    判断处就 return 了，走不到清 `_longPress` 的那行。改在 `endDrag` 的 `moved` 分支里清，
    并且宠物一动就收起按旧坐标定位的菜单（`hideCtx`）。
45. **宠物可能被丢出屏幕外**：`_hasCustomPos` 只在从 localStorage 恢复位置时置 true，
    本次会话内拖拽写了位置却不置位 → `clampToViewport()` 直接 return，
    旋转屏幕或缩小窗口后宠物跑到视口外，按代码自己的注释只能清 localStorage 找回。
    现在拖拽结束即置位（放在 try 外，无痕/配额写失败时内存里的位置同样需要钳制）；
    顺带补上 `pos.y` 的类型校验（原来只查 `x`，y 异常会把 top 写成 `"undefinedpx"`）。

### 赛程表 story.html
46. **取消场被画成凭空多出的败局**。`story_kpl2027.py:479` 给每个 `status:"skipped"`
    的场次都带 `result={"win": False, "score": "-", …}`，而日历标签只看
    `mm.result.win ? '胜' : '负'` —— 季后赛首败之后，后面被取消的场次全部显示成
    「负 对手」并染成败局色；同时 `status==='skipped'` 的格子不给弹详情，
    用户点上去只知道能跳日期，完全不知道这场为什么没了。现按 skipped 分流为
    「取消」，并让取消场也进详情弹窗。
47. `played` 场次若缺 `result`，`mm.result.win` 直接 TypeError 让整月日历渲染不出来 —— 加守卫。
48. **加载失败会把页面结构整个抹掉**：原来 `document.querySelector('.wrap').innerHTML =
   '加载失败：' + e.message` 会连 `#cal`/`#todayCard`/`#statsRow`/`#logList` 一起销毁，
   之后任何渲染都拿不到容器；而在公网隧道下「HTML 顶替 JSON」恰恰是首次访问最常见
   的失败路径。改为写进自己的节点、错误文本走 textContent（不再拼进 innerHTML）、
   并给一个真正能重试的「重试」按钮。
49. **服务端已成功的操作被报成失败**：`doJump` 在 `.then` 里接着改 `viewMonth` 并
   `renderAll()`，任何渲染抛错都会落到同一个 `.catch` 打印「跳转失败」；撤销同理，
   `return reloadAll()` 让一次网络抖动变成「撤销失败」提示，而其实撤销已经生效。
   现在服务端成功之后的重绘单独 try/catch，文案区分「已操作，但界面刷新失败」。
50. SW 壳缓存 bump 到 `xiaoni-shell-v11`（`pet.js` 与 `story.html` 都在 SHELL 里且是

> **给以后的浏览器实测备注**（这次踩到的三个坑，都是一次性成本）：
> 1. 用 `evaluate_script` 往 `localStorage` 播种会在页面 unload 时被 app 的自动存盘覆盖 ——
>    要播种就走服务端 `PUT /api/sessions`，再让客户端同步下来。
> 2. `xiaoni_sessions_v1` 的顶层是**数组**，不是 `{sessions:[...]}`；按后者解析会静默拿到
>    空列表，把「查不到」误读成「已删除」。
> 3. 断言要限定在目标会话内。给另一个会话种下同名字段做对照，会让全库 `includes()` 断言
>    一直为真，把已经修好的行为判成失败。
> 4. 起实例后先确认 `uptime` 很小、且某个本轮修复的特征响应已生效（例如
>    `/api/status` 的 `local.api_key` 返回 `***none`），否则会测在旧进程上。
