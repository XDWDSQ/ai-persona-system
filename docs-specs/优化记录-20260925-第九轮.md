> 第八轮的两条线（后端加固 + 内容质量）都已收口，本轮换了打法：**先修好"验收能力"，
> 再拿两条独立审计线去找真问题**，最后只挑"会让用户真实受伤"的动手。
> 结果：19 套离线测试 + 22 项运行时冒烟全绿；修掉 1 个 P0 级"工程门形同虚设"、
> 2 个 P1 级真实崩溃/数据丢失路径、1 个安全 fail-open、8 个 P1/P2 前端缺陷。

## 零、先说最重要的一件事：这套项目的"验收能力"此前是坏的

本轮开工时，**任何一台机器都跑不起来测试门**，而且失败方式全部指向错误方向。
这是本轮真正的最高优先级问题——修好它之后，后面每一条改动才有证据。

| 症状 | 真实原因 | 为什么危险 |
| --- | --- | --- |
| `run_tests.bat` → `[ERROR] python not found` | 硬编码 `%USERPROFILE%\.openvino\venv\t2i-tts\Scripts\python.exe`，那是原开发机的 TTS 环境；本项目自带的 `venv\` 就在旁边，没人用 | 换机后整条测试门直接空转，而人看到的是"环境没配好"，不会想到"测试根本没跑" |
| 手工跑 `pytest` → `ConnectionRefusedError` 中断收集 | `ops/heic_upload_e2e_test.py` 在 **import 期**就连 `127.0.0.1:8000`；裸 `pytest` 会递归收集 `ops/`、`venv/`、`android/` | 表现为"测试套件坏了"，让人去查测试本身而不是收集范围 |
| `python -m pytest` → `No module named pytest` | `requirements.txt` 里没有 pytest（只在原开发机全局装过） | 换机永远装不上 |
| `run_tests.bat` 输出 `'matically.' is not recognized as an internal or external command` | 该文件行尾是 **LF**，cmd.exe 解析 .bat **要求 CRLF**；多字节中文注释处错位解析，后面的 `set`/`if` 整段失效 | 最阴的一种：脚本"跑了"，但设的变量全丢，报出的错和真实原因毫不相干 |

### 修法

1. **新增 `_find_python.bat`（单一真源）**：按 `PYTHON` 环境变量 → 项目 `venv\` → `.venv\` → PATH 依次探测，
   每个候选都过两道校验——① 解释器能真跑起来（能抓到"venv 的宿主 python 被卸载，
   `python.exe` 报 unable to load python3xx.dll"这种坏环境）② 能 import 调用方要求
   的模块（后端要 `uvicorn`，测试要 `pytest`）。全不可用时打印**具体原因**并非零退出。
   识别 `No module named 'x'` 时用引号做真伪判据（解释器自身报错不带引号），避免误判。
2. **`start.bat` / `restart_service.bat` / `start_test_server.bat` / `start_deploy.bat` /
   `setup.bat` / `run_tests.bat` 全部改走探测**：不再有任何硬编码解释器路径。
   `setup.bat` 顺带重写为「有现成的就用，没有就 `python -m venv venv` 建一个再装依赖」，
   并保留本地 TTS skill 的可选安装。
3. **新增 `pytest.ini`**：显式限定收集边界（`testpaths=.`、`python_files=test_*.py`、
   `norecursedirs=ops venv .venv android __pycache__ ...`），需要真实服务/密钥的运维脚本
   永不进离线收集。
4. **`requirements.txt` 补 `pytest==9.1.1`**。
5. **`run_tests.bat` 重写为 CRLF**，并新增 `.gitattributes` 锁死 `*.bat/*.cmd/*.ps1 → CRLF`、
   其余文本 `LF`、二进制 `binary`——防止编辑器/格式化器/云盘同步端再把它改回 LF。
   文件头写明症状与原因，下次有人遇到能直接对上号。
6. **`runtime_smoke.py` 支持访问口令**：真实服务都开了 `access_token`，此前裸打必然全项 401，
   而且第一个失败点就 `AttributeError`（`body.get` 打在 JSON 字符串上）直接崩，
   完全看不出"其实只是没登录"。现在：先探测门禁 → 需要口令却没给就**明确报错退出**
   （并声明"未写入任何测试数据"），给了口令则自动登录；所有把响应当 dict 用的地方统一
   过 `_as_dict()` 兜底。

## 一、真实缺陷修复（每一条都有"修前必失败的证据"）

### 1. `/api/status` 会被 provider 探测打成 500（P1 崩溃）

`probe_active_provider` 只 `except httpx.HTTPError`。但 `httpx_client` 被关闭后发请求
抛的是 **`RuntimeError: Cannot send a request, as the client has been closed.`** —— 不在
捕获范围内，异常直接冒到路由层，`GET /api/status` 整个 500。
真实触发路径：TestClient 退出 lifespan 会 close 全局 client；前端表现是设置页转圈然后
「加载配置失败」。**这就是本轮开工时的唯一失败用例**（`test_backend_hardening::test_status_mask_cache`）。

修法：离线模式（`AI_DISABLE_EXTERNAL=1`）下探测直接短路为「未探测」，不发任何外部请求；
再加 `except Exception` 兜底，探测失败一律降级成 `(False, 原因)`，**永不打挂 `/api/status`**。

### 2. `server_pkg/sessions_merge.py`：history 里混入非 dict → 核心写入路径永久 500（P1，粘性）

`_msg_key(m)` 直接 `m.get(...)`。`_hist()` 只把「history 不是 list」归一了，
**list 里的元素不是 dict** 这条漏了。后端审计实测：

```
_merge_sessions([{"id":"s1","history":[dict]}], [{"id":"s1","history":["x"]}], {})
  -> AttributeError（经 _is_subsequence / _union_history 三条分支都能触发）
```

**致命的是粘性**：新会话带畸形 history 会被 `by_id[sid] = s` 原样落盘，
此后任何一端正常 PUT 这个会话都崩在同一行，**正常写入路径永远无法自愈**，
只能手改 `sessions.json`。多端同步写入路径等于永久不可用。

修法：`_hist()` 里 `[m if isinstance(m, dict) else {} for m in h]`（替换而非丢弃，
保持下标对齐，避免前缀/子序列判定因索引错位得出错误结论）；`_msg_key` 再加一层入口类型防御。

### 3. 流式对话断流时 story_task 失去强引用（P1，静默丢剧情数据）

`_chat_stream_events` 是 async generator：客户端断流时框架关闭它，生成器帧释放，
`story_task` 就失去唯一强引用，可能被 GC **中途回收** —— 赛果/表白 flag 静默丢失，
日志只留一行 `Task was destroyed but it is pending`。旧实现只在 `except HTTPException`
里 `_detach_bg`，正常收尾与断流路径都没兜住（非流式的 `chat()` 早已有正确 finally，
这是纯遗漏）。

修法：视觉分支与文本主循环**整体包 try/finally**，`finally` 里按 `story_task_settled`
标志决定是否 `_detach_bg`（`_detach_bg` 幂等，对已 done/已托管的任务直接返回）。

### 4. 设置页「陪伴足迹」永久 500（P2，客户端可控数据打挂接口）

`/api/stats` 里 `len(m.get("content") or "")` 遇到数字 `5` 抛 `TypeError`；
`time.localtime(ts/1000)` 遇到 `Infinity` / `1e15` 抛 `OverflowError` / `OSError`。
而 history 是经 `PUT /api/sessions` **原样落盘并驻留**的，所以一条坏数据会让设置页
永久 500，且用户无从知道原因（要删掉那条会话才能恢复）。

修法：`content` 非字符串时 `len(str(...))`；`ts` 加有限性与量程校验（`0 < ts < 4e12`）
并把 `strftime/localtime` 整个包进 `except (OverflowError, OSError, ValueError)`。

### 5. `_access_token()` 安全 fail-open（P2，安全控制静默失效）

旧实现 `except Exception: cfg_tok = ""` —— 把「配置被改坏」当成「用户没配口令」，
access_gate 随即放行：ngrok 公网上 `/uploads/*` 附件与 `/api/sync/stream` 全部未认证可读，
而且没有任何日志痕迹。实测把 config 的 `voice` 节写成字符串、`cloud` 写成数组都能触发。

修法：新增 `_last_good_token`，读配置异常时**回退到上一次成功读到的口令**（继续要求认证），
没有历史口令则回退环境变量，两者都没有才放行，并且每种情况都打 ERROR 日志说明原因。

### 6. `_dup_sim` 把任意两个 2 字回复判成"完全重复"（P2，每轮白烧一次 LLM 调用）

短文本（去空白后 <3 字）没有 3-gram，而 `_jaccard(set(), set())` 约定返回 1.0，
于是 `_dup_sim("在呢", "好的") == 1.0`。后果不是洁癖：服务端复读检测会因此对
**每轮正常寒暄**触发一次额外的 LLM 改写调用（提示词是"用户已指出你重复"，等于用错误的
前提改写正常回复），`role_engine` 里 2 字记忆也会被当重复丢弃。

修法：短文本只在**字面完全相同**时给 1.0；否则用 2-gram 判定（对 2 字文本即精确比较）；
单字因取不到 2-gram，显式返回 0.0——把"空集 ≠ 完全相似"这个约定坑就地收口。

### 7. `deploy/pack_update.py` 调用未导入的 `verify_public_package`（P2，公网打包必崩）

静态检查（ruff F821）第一次跑就抓到：`pack_update.py --public` 走到底必然 `NameError`，
而这一行的语义是**出厂自检**（不通过就不留下可发布的包）。修法：从 `pack_cloud` 导入。

## 三、前端修复（P1 优先，全部经 `node --check` 语法校验）

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| `api()` 全线无超时 | fetch 半开时可以挂几分钟不 settle，调用方 `finally` 永不执行：`state.saving` / `state.uploading` **永久 latch** | `api()` 内建 20s 硬超时（调用方自带 signal 则按能力合并），超时抛中文提示；定时器保留到**读完 body** 再清，否则只等响应头仍会在 `r.json()` 阶段挂死 |
| 会话 PUT 无超时（同步停摆且无提示） | 之后每一次保存（防抖保存、15s 补推、点状态行手动重试）都走同一条 `if (state.saving) return` 早退 → 永久「同步中…」+ 点击无反应，**只能刷新页面** | 该次 PUT 加 `AbortController` + 20s 超时，超时按失败处理（保留 dirty，交给既有补推机制自愈），并在提示里区分"超时"与"网络异常" |
| 附件上传无超时（发送功能整体锁死） | 任一上传卡住 → `Promise.all` 永不 settle → `state.uploading` 永久 true → 发送/编辑/重新生成/重试四个入口被同一闸门同时挡死 | 每个上传自带 60s 上限（大图/弱网比普通请求宽松），`finally` 清理定时器 |
| `refreshStats()` 定义了却从未被调用 | 设置页「陪伴足迹」（含近 7 天柱状图）**永久停在「读取中…」**，100% 复现 | `openSettings` 补一行调用 |
| 保存设置会用"冒充的" `voice_provider` 静默改写语音引擎 | `#voice-tabs` 只有 aliyun/minimax 两个 tab，`pickVoiceProvider` 把 mimo/local 映射成 minimax；只要打开设置点保存（哪怕只改字号），`config` 里 `voice.provider=mimo` 就被静默改成 minimax 且 `manual_provider=true` | 新增 `state.voiceProviderTouched`：只有用户真的点过 voice tab 才提交该字段，否则提交空串（后端 `in (...)` 判断直接跳过 = 保持原值）。后端那行注释（"前端无 mimo tab 时默认 tab 会冒名提交"）正是这个坑的现场记录 |

## 七、未做 / 后续待办（按价值排序，已确认是真问题但本轮未动手）

1. **前端流式收尾竞态**（`makeStreamRenderer` 的最后一次 rAF 可能把气泡写回未清洗原文）：
   服务端 `clean` 比客户端 `stripStyleTag(raw)` 多做了 `_strip_meta_notes` / `_fix_addressing` /
   `_split_narration`，兜底却用"相等判断"，会导致「屏幕上看到的字」与「入库/朗读的字」分叉，
   并连累按内容寻址的删除/重新生成。修法是给渲染器加 `cancel()` 或 `finalized` 标志。
2. **iOS 软键盘遮挡输入栏**：`dvh` 不响应 iOS 软键盘，全仓无 `visualViewport` 处理。
   影响面最广（iPhone 上打字即触发），但**需要在真机确认**再动手，故未改。
3. **`/api/llm-models` 盲 SSRF**：未传 key 且用户自填 base_url 时仍以空 Authorization 发 GET，
   可探测内网/本机（含 ngrok 管理面 4040）。`/api/llm-quota` 有"无 key 就 400"的反证说明此处遗漏。
4. **`/api/health` 在配了口令时仍泄露运维信息**（磁盘余量、分供应商 token 消耗、订阅者数），
   `/api/activity` 暴露"最近 5 分钟是否在聊天"。
5. **事件循环里同步调 `_get_story_manager()`**：首次构造持 `threading.Lock` 做磁盘 IO，
   与 lifespan 预热撞上会冻住整个事件循环（SSE 全卡）。async 路径应走 `asyncio.to_thread`。
6. **会话静默截断 500 条**（无告警/归档），超出部分从服务端永久消失。
7. `pet_process.py` 全量帧驻留内存（与注释"内存恒定"不符），长素材可能 OOM。
8. 侧栏每条消息重建（去重 key 含原始 `updatedAt`）、桌宠 1.1s 定时强制布局、
   `.toasts` 层级低于设置遮罩、`#theme-tabs` 不存在导致 auto 主题不可达、
   `confirmDialog` 无重入保护、SW 缓存 302 后的登录页（未判 `res.redirected`）等 P2 项。
9. 项目级：`server.py` 仍有 6500 行/320KB（本轮未再拆分，避免在缺少端到端覆盖时做大手术）；
   前端 `app.js` 4600 行同理。

---

## 八、一句话总结

第八轮之前的优化都在"让功能更好"，这一轮补的是"**让改动可验证**"——
把一条会静默空转的测试门修成真门，然后用它挡下了 2 条 P1 崩溃/数据丢失路径、
1 条安全 fail-open、5 条会让用户"只能刷新页面才能恢复"的前端锁死缺陷。
