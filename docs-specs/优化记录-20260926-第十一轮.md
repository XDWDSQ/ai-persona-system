## 一、四条实测确认的缺陷

全部先写成一次性探针脚本，对**当前工作树**跑出真实结果，再改代码。

### 1.1 P1 · SSRF 闸只比字符串 → URL 里"本机"的等价写法整片漏过

`_url_is_blocked_target` 原实现拿 `urlparse().hostname` 和
`{"127.0.0.1","localhost","::1","0.0.0.0","[::1]"}` 比，再用 `startswith("127.")` 兜一下。
实测（本轮探针输出，`ALLOW` = 闸放行）：

```
BLOCK http://127.0.0.1:4040/api
BLOCK http://localhost:9000/v1
ALLOW http://2130706433/v1          # 十进制整型 IPv4 = 127.0.0.1
ALLOW http://0x7f000001/v1          # 十六进制整型
ALLOW http://017700000001/v1        # 八进制整型
BLOCK http://127.1/v1               # 只是碰巧被 startswith("127.") 拦住
ALLOW http://[::ffff:127.0.0.1]/v1  # IPv4-mapped IPv6
ALLOW http://localhost./v1          # 尾部点（FQDN 绝对写法）
```

这些写法 **httpx 全都会真的连过去**，不是"字符串不一样但连不上"。后果：
被泄露/绕过的口令持有者可以填 `http://2130706433:4040/api` 让服务端去读本机
ngrok 管理面并原样回显，或让服务端打自己（`http://2130706433/`）。

### 1.2 P2 · 端口笔误把端点直接打成 500

`parsed.port` 的读取在 `try/except` **之外**。`urlparse` 能解析 `http://h:99999/v1`，
但 `.port` 抛 `ValueError`，一路冒到端点。实测（带真实口令、禁用外部调用）：

```
POST /api/llm-models {"base_url":"http://example.com:99999/v1"} -> 500 服务器内部错误
POST /api/llm-quota  {"base_url":"http://h:abc/v1"}             -> 500 服务器内部错误
```

手填 API 地址时这是最常见的笔误之一，用户看到的是"服务器内部错误"而不是"端口不合法"，
日志里还多一条未捕获异常 traceback。

### 1.3 P1 · 域名解析到本机（`127.0.0.1.nip.io`）整条路绕过

只做字面量判定的话，这一闸是**一次 DNS 就能绕过**的：挂个免费 wildcard DNS
（`nip.io` / `sslip.io`）就能把 `127.0.0.1` 藏在一个合法域名后面。
项目自带的 `verify_chain.py` 早就在用"先解析再 `ipaddress` 判型"的口径，
服务端这边却没有。

### 1.4 P1 · `_behind_local_proxy` 把"私网"当自己人 → 爆破锁定可无限绕过

原判据 `peer.is_loopback or peer.is_private`。可服务默认 bind `0.0.0.0`，
**局域网里任何一台机器**直连过来对端都是私网地址。实测：

```
127.0.0.1     behind_local_proxy=True   client_ip=1.2.3.4   <- 同机代理，正确
192.168.1.50  behind_local_proxy=True   client_ip=1.2.3.4   <- 局域网直连，错的
10.0.0.7      behind_local_proxy=True   client_ip=1.2.3.4   <- 同上
```

于是 `_client_ip` 采信了攻击者自己塞的 `X-Forwarded-For`。对同一对端连发 39 次
不同 XFF 的实测结果是：**39 个互不相同的限流桶**——"8 次失败锁 10 分钟"的爆破防护
变成可无限重试（每请求换一个 XFF 就重新开始计数）。

### 1.5 P1 · `allow_origins=["*"]` 给出一个分布式口令 oracle

第十轮的注释写着"跨域放开仅在配置访问口令时安全"，但 `/api/login` 在口令校验
**之前**，而它的跨源响应带着 `Access-Control-Allow-Origin: *`。实测：

```
POST /api/login  Origin: https://evil.example  -> 401 + ACAO: *
OPTIONS /api/login（预检）                      -> 200 + ACAO: * + ACAM: content-type
```

恶意页面因此可以跨源逐个猜口令，并凭 `ACAO:*` **读懂**返回 200 还是 401。
更糟的是这不受按 IP 的锁定约束：每个访客浏览器都是一个不同出口 IP，
攻击者只要把页面挂出去，就有成千上万个"干净"的限流桶可用。

## 二、修法

### 2.1 新增 `_host_to_ip` / `_ip_is_internal`：把等价写法收敛成同一个 IP 对象

```python
ip = ipaddress.ip_address(h)                # 直解：点分四段 / IPv6
    except ValueError:
        ip = ipaddress.ip_address(socket.inet_aton(h))   # 兜底：整型/十六进制/八进制/短式
    if isinstance(ip, ipaddress.IPv6Address) and ip.ipv4_mapped is not None:
        return ip.ipv4_mapped               # ::ffff:127.0.0.1 取内层再判型
```

`socket.inet_aton` 恰好接受整型/十六进制/八进制/短式这四种旧写法，且越界值与纯域名
一律拒绝 —— 两步就把 1.1 里所有写法收敛掉。另附加：

- hostname 先去 `[]`、去尾部点、去 IPv6 作用域 id（`%25eth0`）再判；
- 回环**域名**（`localhost` / `localhost.localdomain` / `ip6-localhost`）单独一张表，
  这样 `localhost.` 不再靠运气；
- 内置地址判据扩到 `is_loopback or is_unspecified or is_link_local`
  （链路本地整段 `169.254.0.0/16` + `fe80::/10`，`169.254.169.254` 自然被覆盖）；
- **刻意不含 `is_private`**：局域网自建 ollama/llama.cpp 是真实用法，误伤代价太高
  （第九轮就是这个取舍，本轮沿用）。

端口先安全取一次：`parsed.port` 包在 `try` 里，失败返回"端口不合法"而不是冒异常（修 1.2）。

### 2.2 新增 `_url_resolves_to_internal`：解析后复查

用 `loop.getaddrinfo`（线程池内执行）而不是同步 `socket.getaddrinfo` —— 后者在解析器
无响应的机器上会把事件循环整个卡住数秒，SSE 全跟着停。再套 `asyncio.wait_for(timeout=3)`
兜住线程池里那次调用。

- 解析到回环/链路本地/未指定 → 拒绝，消息里带上 `域名 → 解析出的 IP`（排障友好）；
- **解析失败/超时一律放行**：真正的报错交给随后那次真实请求，不该因为"DNS 一时不通"
  把用户的正常域名判死；
- IP 字面量直接跳过（不做无谓的 DNS 查询）；
- 与 config 里已配地址完全一致时跳过（机主自己的选择）。

两个端点（`/api/llm-models`、`/api/llm-quota`）依次调用字面量闸与解析闸。
解析函数抽成模块级 `_getaddrinfo` 是为了给离线用例留替换缝。

### 2.3 `_behind_local_proxy` 判据收窄到 `is_loopback`

同机代理（ngrok 等）的连接**必然**来自回环，所以只保留 `is_loopback`。
局域网直连的对端回落到它自己的真实 IP，限流桶不再可被伪造的 XFF 轮换。
若日后真把反代放到另一台机器上，需要的是**显式的可信代理白名单**，
而不是"私网即自己人"这种一放就是一整个网段的猜测（已写进 `AGENTS.md`）。

### 2.4 跨源：默认不给任何 CORS 头，`access_gate` 两种模式统一 403

- 删掉无条件 `allow_origins=["*"]`；改为**只在 `config.json` 配了
  `cors_allow_origins` 时**才注册 `CORSMiddleware`（显式点名来源，`allow_credentials=True`）。
  本项目页面与 API 同源，正常使用一个 CORS 头都不需要。
- 跨源判定搬进 `access_gate`，**两种模式都过**：带 `Origin` 且与本次请求的 `Host`
  不一致（且不在白名单里）→ 直接 403。不做"少给几个响应头让浏览器自己拦"——
  那对非浏览器调用方毫无约束，而登录端点的爆破 oracle 正是被非浏览器放大最多。
- `Origin: null`（sandbox iframe / `file:` 页面 / 跨源重定向）一律不可信：
  `urlparse("null").netloc` 是空串，不特判就会和空 Host 比出"相等"。
- 默认端口归一化（`http://h` ≡ `h:80`）、host 大小写与尾部点归一，
  避免在 127.0.0.1 / localhost / 局域网 IP / 隧道域名之间切换时误伤自己。

## 四、未做 / 后续待办（按价值排序）

1. **DNS rebinding 的 TOCTOU 残余**：解析闸在**校验时**解析一次，httpx 在**连接时**
   再解析一次，两次之间域名可以变。真正的闭法是"把解析出的 IP 钉住再连"
   （自定义 transport / 固定 `Host` 头），改动落在 httpx 客户端装配处，本轮没做。
   静态版（`nip.io` 这类域名恒解析到本机）已经挡住。
2. **同源判定挡不住"攻击者域名解析到本机"**：DNS rebinding 成功时
   `Origin` 与 `Host` 真的一致，浏览器视角就是同源。要挡需要 Host 白名单或
   校验 `Host` 是否为已知的本地访问方式，属另一条独立的加固线。
3. **没有可信代理白名单**：反代放在另一台机器上时，它的 XFF 现在**不被采信**
   （偏严、fail-closed）。真需要时再加 `trusted_proxy_ips` 之类的显式配置，
   而不是回到 `is_private`。
4. 第十轮的其余待办**原样保留**：剧情管理器 8 处 async 路径；
   会话超限的内容归档 + 前端 `truncated` 提示；`android/` 存档工程的引用未改；
   `pet_process.py` 两遍全量驻留未改流式；`server.py` 6834 行 / `app.js` 4800 行的拆分；
   本机 `.pytest_cache` / `%TEMP%\pytest-of-31557` 的 ACL 损坏（仍靠"排除收集 +
   把 cache/basetemp 指到项目内"绕过）。
5. `CORS` 白名单是**导入期**读取的，改 `cors_allow_origins` 需重启服务。
   已写进 README 的配置表；若日后要免重启，得把 CORS 头改成请求期动态生成。
