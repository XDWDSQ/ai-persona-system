## 一、让"验收能力"可信（本阶段第一优先级）

### 1.1 `test_role_news_v2` 用 `✓`/`✗` 报告结果，被管道调用时必然崩

| 项 | 内容 |
| --- | --- |
| 症状 | 该套件在 `run_tests.bat` / 任何管道或重定向下 `UnicodeEncodeError`，整套判失败，但报错指向"编码/环境" |
| 真实原因 | `:130`/`:133` 打印 `✓`(U+2713)/`✗`(U+2717)，GBK 编不出。`chcp 65001` 只改**控制台代码页**；stdout 是管道/重定向时 CPython 取的是 locale（cp936/GBK），改不了 |
| 为什么危险 | ① 门变红却指向环境，掩盖真问题；② 更糟：它在**第 1 组断言**处就崩（异常被 `except Exception` 吞掉，又在失败分支再打一次 `✗` 直接冒泡出进程），**第 2~8 组断言从未执行** —— `_build_rule_cards`/`_cards_to_summary`/`_merge_cards`/`_build_timeline`/`_emotion_text`/`_log_role_news_missing`/`_load_role_news` 全没验过 |

**修复前的决定性证据**（一行环境变量就分出真伪）：

```
set PYTHONIOENCODING=utf-8 && venv\Scripts\python.exe test_role_news_v2.py
→ 23 通过 / 0 失败      # 断言本身全是好的，失败纯属报告器
```

修法：
- 标记改成 ASCII 的 `[PASS]`/`[FAIL]`（与其余 20 套一致）；
- `check()` 改为**先打印后计数**（旧实现先加计数后打印，打印崩了就出现"计数 +1 但一条都没输出"的错位）；
- 新增**断言数下限**：真实模块 23 条、降级路径 20 条，低于下限直接判失败。

**反证（旧行为必失败）**：把被测模块换成"什么都没有"的空 dict 后

```
[FAIL] 实跑断言数 1 低于预期下限 20（被测函数被改名/搬走时 hasattr 守卫会静默跳过，而门仍是绿的）
floor_negative_exit_code = 1
```

旧实现没有下限断言，这种情况下会**0 断言通过、退出码 0** —— 门全绿但什么都没验。
本套件每组都用 `hasattr(mod, ...)` 守卫，而项目正有 `server.py` 模块化计划，这个假绿灯比崩溃更隐蔽。

### 1.2 `chcp 65001` 管不了管道：`run_tests.bat` 加 `PYTHONIOENCODING=utf-8`

一行覆盖全部子进程，顺带防住未来任何套件打印 GBK 编不出的字符。文件头把
"chcp 只影响控制台、不影响管道"这个坑写清楚了（否则后人会以为已经管了）。

| 为什么危险 | ① 用户在设置页调一次人设 → 整条测试门变红，把"内容改动"误报成"代码回归"；② 角色被删/改名直接 `KeyError` 中断，报错与真实原因无关；③ `_story_role()` 恰好为真时**静默 return**，又一处假绿灯 |

- 缺角色/缺字段 → 显式判失败（不再 KeyError）；`_role_persona()` 统一入口。

## 二、后端真缺陷

### 2.1 P1 · sessions 里的非有限浮点会让**所有设备的多端同步永久停摆**（粘性）

| 项 | 内容 |
| --- | --- |
| 证据 | 落盘 `_dump` 与读取 `_render_sessions_body` 都未传 `allow_nan=False` → `inf/nan` 写成 JSON 字面量 `Infinity`/`NaN`（**RFC 8259 非法**）→ `GET /api/sessions` 的**响应体本身永久非法** |
| 触发 | 任一客户端 PUT 一个 `1e400`（**语法完全合法的 JSON 数字**，解析为 inf），或同步盘回滚出带 `Infinity` 的文件。不需要是浏览器发的 |
| 后果 | Python 侧一切正常，但每台设备的 `r.json()` 都抛错、重试 3 次后放弃 → 多端同步彻底不动，而服务端 `/api/stats`、`/api/status` 全绿、日志无痕。**只能手改文件自愈，手机端还改不了** |
| 现有回归为何没抓到 | `test_backend_hardening` 的 sandbox 早就在写 `inf/nan` 进 `sessions.json`，但只打了 `/api/stats` —— 没打 `GET /api/sessions` |

机制取证（走真实代码，只换 `allow_nan` 开关）：

```
OLD_DUMPS_CONTAINS_INFINITY: True       NEW_DUMPS_CONTAINS_INFINITY: False
OLD_STRICT_PARSE: REJECTED -> illegal Infinity     NEW_STRICT_PARSE: ACCEPTED
GUARD_ALLOW_NAN_FALSE: REFUSED -> Out of range float values are not JSON compliant: inf
```

修法（三层防御）：
1. 新增 `server_pkg/sessions_merge.py::_sanitize_nonfinite()`：递归把 `inf/-inf/nan` 换为 `None`，
   **只清洗值、不丢键**（消息下标对齐不被破坏）；
2. `put_sessions` 入参清洗 + `_read_sessions_cached()` 加载清洗 → **存量坏文件自愈**（粘性的关键）；
3. `_dump` 与 `_render_sessions_body` 都加 `allow_nan=False` 作最后一道闸（写盘侧 `ValueError` → 400）。

回归：单元（清洗语义）+ 端点「PUT `1e400` 后响应体能被**严格** JSON 解析」+ 端点「预置含
`Infinity` 的存量文件 → 首次 GET 即恢复可解析（自愈）」。

### 2.2 P1 · 口令门禁仍可 fail-open（`load_config` 静默降级）

| 项 | 内容 |
| --- | --- |
| 现状 | 第九轮只兜住了 `load_config()` **抛异常**那一种损坏。而它遇到最常见的损坏 —— **非法 JSON / 读不到 / stat 失败** —— **不抛异常**，而是静默 `return _default_config`，那份默认配置里**没有 `access_token` 键** |
| 后果 | 门禁把"配置坏了"读成"用户没配口令" → 全放行，**日志里一个字都没有**。ngrok 公网下 `/uploads/*`、`/api/sync/stream`、全部 `/api/*` 匿名可读 |
| 触发条件 | 在本项目非常现实：跑在移动云盘同步盘上，`config.json` 很容易被同步客户端截成半截 |

**决定性取证**（同一份坏 config，只换 `_access_token` 的实现）：

```
OLD_IMPL_STATUS: 200              # 第九轮那版：匿名直接读到全部会话，门禁敞开
NEW_IMPL_STATUS: 401              # 现版本：fail-closed
NEW_IMPL_WITH_TOKEN_STATUS: 200   # 不误伤本人
```

修法：新增模块级 `_cfg_load_ok`，由 `load_config()` 在三条降级早退路径置 `False`、正常路径置 `True`；
新增 `_token_failsafe(reason)` 把**两类损坏**（抛异常 / 静默降级）收敛到同一条策略：
历史口令 → 环境变量 → 都没有才放行，且每个分支都打 ERROR（绝不记录口令内容）。

回归：非法 JSON → `/api/sessions` 必须 401、带正确口令仍 200；反向用例：健康配置且确实未配口令
→ 仍返回 `None`（不破坏本机直连）。

### 2.3 P1 · 爆破防护只护 `/api/login`，Bearer 路径**全程绕过**

失败的计数/锁定/留痕/退避原先只挂在 `POST /api/login` 上，但**真正守门的是 access_gate →
`_auth_ok()`**。攻击者对任意 `/api/*` 逐个换 `Authorization: Bearer <猜测>` 就能无限次尝试口令
—— 不计数、不留痕、不退避，那套防护完全不参与。

修法：抽出 `_record_auth_failure(ip, source)`（计数 + 留痕 + 复用 `_login_track`/`_client_ip`/
`_purge_login_track`），**门禁的鉴权失败分支与 `/api/login` 共用同一套**；失败后固定
`_LOGIN_BACKOFF_SECONDS` 退避。

刻意**不**在门禁改状态码（仍是 401/302）：前端的未登录处理认的就是 401（`app.js` 见 401 跳
`/login`），改成 429 会掉进通用错误分支反复重试。限流效果由"每失败一秒"提供。

### 2.4 P2 · `/api/llm-quota` 缺 SSRF 闸（与已修好的 `/api/llm-models` 不一致）

该端点会按调用方给的 `base_url` 拼出 quota 端点并**真的发 GET**，却完全没有
`_url_is_blocked_target` 检查 —— 口令一旦泄露/被绕过，SSRF 靶点就从 `llm-models` 转移到它
（可打内网 / 本机 ngrok 管理面 4040）。修法：复用同一道闸（一个 `if`），并补端点回归
（含"公网地址不被误拦"的反向用例）。

### 2.5 P1 · 剧情管理器：构造失败后**每个请求**都在事件循环里重建

`StoryManager` 的首次构造要 mkdir / 读 state / 读整季日历（缺失时现场生成并写盘）/
`_atomic_write` 失败重试，**全程持 `_story_manager_lock`**。而一旦构造抛异常，`_story_manager`
会永远停在 `None` —— 于是此后**每一次**剧情角色请求都在事件循环里重做这段磁盘 IO，把全场 SSE 一起冻住。

修法：**失败负缓存** `_STORY_RETRY_COOLDOWN = 60s`，冷静期内直接返回 `None`（不做磁盘 IO、不抢锁）。
把"每次都卡"降为"最多每 60s 卡一次"。**残余见"未做"第 1 条。**

### 2.6 P2 · 会话截断**先丢置顶的**

截断与入站排序只看 `updatedAt`，而前端列表是**置顶优先** → 会话数触及上限时，
**用户主动置顶（=最在意）的那几条最先被丢**，且无任何提示。
修法：新增 `_sess_order_key`（`(pinned, updatedAt)`）作为**唯一**排序键，入站截断与合并截断都改用它，
与前端语义一致、也不再有第二份实现可漂移。

### 2.7 P2 · uploads 清理循环**先睡 6h 再扫** → 频繁重启时永不执行

`while True: await asyncio.sleep(6h)` 在扫描**之前**，而 `restart_service.bat`/自动部署比 6h 更频繁时，
这一轮扫描**永远不会发生** → `uploads/` 只增不减 → 盘满 → 会话与配置保存失败（真丢数据）。
修法：`sleep` 移到循环尾部（首轮立即扫一次），与 TTS 缓存清理的 `force=True` 首扫对齐。

### 2.8 P2 · 关闭固定等满 5s；`_bg_tasks` 跨 lifespan 累积

集合里含两个**从不取消**的无限循环（uploads 清理、角色动态巡检）：`asyncio.wait(timeout=5)`
每次重启都要白等满 5s，而且它们永不 done → done 回调永不触发 → 每进一次 lifespan 就多攒 2 个死任务，
逼近 `_BG_TASKS_MAX=200` 后 `_spawn_bg` 会**丢弃一切后台任务**（含记忆/情绪写入的 `_post_process_chat`）。

修法：`_spawn_bg` 返回任务对象；lifespan 关闭时显式 cancel 这两个循环并 `gather` 收尾；
`_spawn_bg` 达到上限的日志级别 WARNING → **ERROR**（那时丢的是数据，默认级别下必须看得见）。

### 2.9 P2 · sessions 指纹的 sha1 仍在事件循环里算

序列化/压缩早就走了线程池，唯独指纹漏了。5–32MB 文件 ≈ 10–120ms 事件循环停顿 → SSE 心跳抖动。
修法：GET/PUT 两侧都 `await asyncio.to_thread(_sessions_fp, raw)`。

### 2.10 P2 · `sessions_truncated.log` 无轮转（对照 `role_news_missing.log` 有）

同类日志各写一份，"一个有就等于都有"的错觉让它长期无声增长。
修法：抽出通用 `_rotate_jsonl_if_needed(path, max, keep)`，两处共用（超 1MB 保留尾部 256KB、按整行截断）。

### 2.11 P2 · 关键降级路径只打 DEBUG，默认级别下**完全看不见**

用户报"天气/现实动态一直空着"时，日志里什么都没有，只能人肉复现。
修法：天气缓存读/写失败、角色动态写失败、记忆/状态收集失败、总结失败、刷新跳过、
巡检 tick 失败等**缓存与链路 IO 失败**一律 WARNING（正常路径仍零刷屏）。

### 2.12 原子写加重试（**本轮观测到的真实失败**）

全量跑 pytest 时抓到一次：

```
PermissionError: [WinError 5] ... config.28356.<uuid>.tmp -> .../config.json
```

不是"盘坏了"，而是**移动云盘同步盘/杀软会对刚落盘的文件短暂持有句柄**，几毫秒后重试即成功。
旧实现让这种瞬时占用直接冒成 500 —— 用户看到"保存设置失败"，而配置其实没保存成功，
排查方向还会被带偏到"磁盘故障"。`story_kpl2027` 与 `role_engine` 的原子写**早就各自做了同样的重试**，
只有 `server.py` 这几处漏了。

修法：新增 `_atomic_replace(tmp, target, attempts=3)`（首次不 sleep，之后 0.05/0.1s），
用于 config / sessions / weather / role_news / llm_usage 五处原子写；含 sleep 故只在线程池里调。

### 2.13 P3 · 注释漂移与小防御

- `/api/status` 脱敏缓存的注释还写着旧实现"按 `id(cfg)` 缓存"，实际已是 mtime + env 签名 —— 改对；
- `_behind_local_proxy` 的 docstring 仍提 cloudflared → 只留 ngrok；
- `_status_config_parts` 补一句"调用方只能写返回值顶层新键，改嵌套值会污染缓存本体"。

## 三、前端缺陷

### 3.1 P1 · `.toasts` 层级低于设置遮罩 → **保存设置失败对用户完全不可见**

`.toasts{z-index:80}` < `#settings{z-index:998}`，而"保存设置失败"的提示正是 toast
→ 设置**看起来保存成功了，实际后端配置没变**；设置面板内的其它失败提示同理。
修法：`.toasts` → `z-index:1300`（高于设置 998、确认框 1200、灯箱 1002）。

### 3.2 P1 · Service Worker 把 **302 后的登录页**当作聊天页缓存

`sw.js` 导航分支只判 `res.status === 200`，**没有 `res.redirected`**。服务端未认证的页面请求返回
`302 /login`，fetch 默认跟随 → 最终 200 且 `res.url` 指向 `/login` → 登录页被写进 chat 页的缓存 key。
cookie 过期/新设备时，离线启动 PWA 得到的是**登录页**。
修法：写缓存前加 `!res.redirected` + pathname 比对。

### 3.3 P2 · 流式 AI 气泡缺 `dataset.hidx` → 删除**误删更早的同文消息**

`dataset.hidx` 只在用户消息/历史渲染/问候三处写入，流式气泡从不设置 → `removeFromHistory`
只能退回"按内容**正序**匹配第一条" → 模型复读时删掉的是**更早那条**（重生成走倒序，相对安全）。
修法：入库处记下 `aiIdx`（剧情 event 会紧接着再 push 一条，`len-1` 已不是它），气泡生成后写回
`div.dataset.hidx`。

### 3.4 P1/P2 · `/api/tts` 与同步轮询的 fetch **没有任何超时** → 朗读按钮永久卡死

| 位置 | 后果 |
| --- | --- |
| `/api/tts` | 半开（ngrok 抖动/切网/后端重启未发 RST）时 Promise 永不 settle，而它又被 `state.ttsInflight` 缓存 → "点重试"拿到的是**同一个死 Promise**，朗读按钮永久停在"正在合成…"，只能刷新页面 |
| `fetch(msg.audio)` | 同上，整个朗读流程卡住 |
| `/api/sessions/fingerprint`（每 30s 一发） | 挂起的请求**一条条占满同源连接池**，把聊天/保存请求一起拖住 |
| `/api/sessions`（全量拉取） | 同上 |

修法：`apiTimeoutSignal(outer, ms)` 支持自定义预算（原本只有 20s）；TTS 用 60s、读缓存音频 20s、
指纹探测 20s、全量拉取 20s，且**定时器都保留到读完 body 再清**（只等响应头就清的话，
半开在 `r.json()`/`r.blob()` 阶段仍会挂死 —— 正是要修的那类卡顿）；TTL 超时映射成可读中文；
`ttsInflight` 在 `finally` 清理。一并修 `ttsAndPlay(...)` 四处调用点未 `.catch`（前置段在 try 之外会
产生 unhandled rejection）。

### 3.5 P2 · `#theme-tabs` 不存在 → `auto`（跟随系统）主题**不可达**

`app.js` 有两处绑定 `#theme-tabs .set-tab`，而 `chat.html` 里根本没有这个元素
（只有 `#role-tabs`/`#font-tabs`/`#voice-tabs`）→ `auto` 只能靠 localStorage 初始化读到，
没有任何入口能设成它（静默死代码）。
修法：照 `#font-tabs` 的 markup 补三态按钮（`data-theme=dark|light|auto`）—— 绑定契约本就如此，无需改 JS。

### 3.6 P2 · `confirmDialog` 无重入保护

每次调用都往同一个 `#confirm-modal` 再挂一遍监听并覆盖文案，连点/移动端双击会让两个 Promise
被同一次点击同时 resolve —— **用户看到的是第二个问题，回答的却是第一个**。
修法：模块级 `_cfBusy`，已打开时直接 `return Promise.resolve(false)`，`close()` 复位。

### 3.7 P2 · 桌宠 1.1s 定时**强制同步布局**

`dodgeCheck` 每轮做 `getBoundingClientRect` + `getComputedStyle` + `offsetParent`（强制 reflow），
流式输出期间（每帧都在改气泡尺寸）会造成可见掉帧，后台标签页里也白烧电。
修法：2s + `visibilityState` 门控，切回前台立刻补一次。（事件驱动版见"未做"。）
