# 项目全方位优化报告

> 日期：2026-08-29 · 范围：全项目（后端 / 前端 / Android / 数据 / 仓库卫生）
> 立场：这是你每天在用的私人产品，报告只回答一个问题——**怎么让它用起来更舒服**。
> 注：2026-08-05 已做过一轮性能专项优化（gzip / 缓存 / 渲染合并，见 `docs-specs/优化报告-20260805.md`），本报告不再重复那些已落地项，聚焦**产品、体验、信息架构与仓库卫生**。

## 一、项目现状

这是一个**单用户、单角色、单页面为主**的 AI 陪伴系统：

- **真实使用画像**（从 `data/sessions.json` 实测）：5 个会话里只有 1 个真实会话（129 条消息），其余 4 个是空的"新对话"；实际在用的角色只有"大帅"一个；LLM 实际走云端 MiniMax-M3，TTS 走 MiniMax 克隆音色（阿里云备份）。
- **两个入口**：桌面浏览器 + 手机 APK（APK 打开即聊天页，其他页面会被原生层拦回聊天页）。
- **代码底子意外地好**：SSE 攒批、mtime 缓存、原子写、多端墓碑合并、失败重试气泡、防抖保存、动画门控……大量"曾经踩过坑"的防御式代码，注释质量高。
- **但项目外围已经长满了杂草**：26+ 个同步盘冲突文件、约 500MB `_archive`、556MB TTS 缓存躺在云盘同步目录里、4 个前端页面里 3 个是"展示给外人看"的营销页而你的手机端根本打不开它们。

一句话总结：**核心页面（chat.html）已经打磨到 85 分，但它周围挂着一圈早已不用的旧产品叙事（本地模型、官网落地页、声音克隆 demo 文案），以及一个正在持续制造冲突文件的同步盘布局。**

## 二、项目核心结构

```
AI拟人系统/
├─ ai-persona-system/            ← 实际运行根目录（有独立 git 仓库）
│  ├─ server.py                  4950 行单体后端：chat/tts/搜索/天气/角色动态/会话/登录/静态托管
│  ├─ role_engine.py             742 行角色引擎（记忆/情绪/时间），质量最好的一份代码
│  ├─ minimax_llm.py / minimax_clone.py / pet_process.py   云端适配与素材工具
│  ├─ config.json                含明文 API key + 两份重复的大段 persona
│  ├─ xiaoni-ai-persona/pages/   前端 5 页（chat 3959 行为核心）+ pet.js 桌宠
│  ├─ android/                   APK：assets/pages 是前端的手工 xcopy 副本
│  ├─ data/                      sessions/memory/state/tts_cache(556MB)/uploads
│  ├─ llm/                       本地 LLM 启动脚本（模型文件已删除，功能实际已死）
│  └─ test_*.py × 7 + 大量 *.bak / *_冲突文件*
├─ _archive/                     ≈500MB 历史归档（legacy-* 系列）
├─ .workbuddy/ .tmp-gmi-audio/   其他工具的遗留
└─ AGENTS.md / README.md + 各自的冲突文件副本
```

**数据流**：chat.html ⇄ `POST /api/chat`（SSE 流式，搜索/视觉/长文续写在服务端循环）→ 回复入库 localStorage + `PUT /api/sessions`（多端合并 + SSE 广播）→ `POST /api/tts`（磁盘缓存 + 前端 blob 缓存）→ pet.js 监听 `pet:state` 事件联动桌宠。链路清晰，没有架构性问题。

## 三、当前优点（这些不要动）

1. **chat 主链路的体验细节非常扎实**：流式渲染帧合并、贴底跟随（上翻不打断）、失败可重试气泡、流中断保留半截回复、编辑消息截断重生成、会话多端墓碑合并——这些是真正的"用过才发现"的功能。
2. **role_engine.py 设计干净**：与 FastAPI 解耦、原子写、损坏自愈、记忆去重、情绪平滑限幅，单测覆盖。
3. **视觉系统统一**：Vercel 风格 token（深色主题）、克制的设计语言、动画全部走合成器属性、`prefers-reduced-motion` 兜底。整体观感是"高级、干净"的。
4. **移动端认真做过**：safe-area、dvh 高度链、长按菜单、iOS 16px 防缩放、触摸目标重排——不是敷衍的 media query。
5. **后端稳**：后台任务上限、SSE 排除 gzip、上传白名单+HEIC 转码、会话破坏性合并前自动备份。

## 四、当前主要问题（按你的优先级排序）

### 🔴 P0 —— 影响日常使用

**P0-1 仓库住在同步盘里，正在持续制造垃圾和风险**
运行目录是 `D:\移动云盘同步盘\AI拟人系统`（Desktop 下的目录是另一份）。后果已经全部显形：
- 26+ 个 `*_冲突文件20260827*`（server.py、config.json、chat.html 全都有冲突副本——**如果哪天你恢复错了冲突文件，服务就直接坏了**）；
- `data/tts_cache/` 556MB wav 会被云盘客户端反复扫描上传，`sessions.json` 两端同时写加剧冲突；
- git 仓库放在同步盘里，`.git/objects` 上万个小文件同步压力巨大。

**P0-2 config.json 里三把明文 API key + 弱口令 `520TDJ`**
ngrok 免费版是公网地址。`/api/status` 在有 access_token 时会**明文回传密钥**（为前端回填设计），等于密钥随每个登录会话在公网传输。key 应迁去 `.env`（后端已支持 env 覆盖，前端只需不再回填明文）。

## 六、性能问题

先说结论：**当前规模下没有真实性能瓶颈**——8-05 那轮优化把该做的都做了。129 条消息的会话渲染、SSE 攒批、TTS 三级缓存都工作良好。剩余事项按"预防"性质列出：

1. **无虚拟列表**：消息列表是全量 DOM。129 条没问题，但如果你养成单会话几千条的习惯，切会话/长会话会开始掉帧。**观察项**，等单会话 >500 条再上分页/虚拟化，不要现在做。
2. **Google Fonts 外链**：网络不通时每次页面加载都白等一个请求超时（虽不阻塞渲染）。改为本地 woff2 或直接删（Geist 与系统字体差距小）。
3. **tts_cache 556MB 且在同步盘**：不是服务性能问题，是同步盘 IO/上传压力。限额从 8GB/500 个调小（如 1GB/200 个），并让它离开同步范围。
4. **多端同步 PUT 是全量 payload**：sessions.json 目前 75KB 无所谓；将来上 MB 后可改增量。**观察项**。
5. `_extend_long_form` 续写每轮都重建完整 messages（人设 ~2.5KB × 轮数）——云端上下文窗口大，可接受。**不动**。

## 八、架构问题

架构本身（FastAPI 单体 + 静态前端 + JSON 文件存储 + APK 内嵌页面代理）**对这个项目是正确的**，不要微服务化、不要上数据库。真正的问题只有两个：

1. **前端"构建"是手工的**：`xiaoni-ai-persona/pages` → `android/app/src/main/assets/pages` 靠 README 里一行 xcopy。人肉同步必然漏（这次冲突文件已经进了 assets）。需要一条命令的同步脚本 + 构建前强检。
2. **server.py 单文件到了可拆的临界点**：天气（含 300 城市表）、角色动态、TTS、搜索、会话同步各自 300-500 行，边界清晰。拆成 `modules/` 包（不改任何接口）能让以后改天气不用在 5000 行里找位置。这是"容易继续开发"投资，优先级低于体验项。

## 十三、如果这是我的项目，我会怎么改

> 核心判断：这个产品 90% 的生命发生在**一个页面、一个角色、一块手机屏幕**上。所以一切优化围绕"把 chat.html 做成唯一的产品"展开。

1. **先搬家再装修**。我会把运行目录整体移出同步盘（同步盘只放 `docs-specs` 和导出的对话存档），`tts_cache` 限额砍到 1GB。冲突文件是最大的一颗雷——先把雷排了，再谈别的。做完这一步，项目从"随时可能坏"变成"稳定地基"。

2. **删到只剩产品**。index/architecture/status/roles 四个页面是我写给"假想用户"看的，而真正的用户是我自己，在手机上。删掉它们，侧栏只留：会话、角色、设置。前端从"一个应用加四个展厅"变成"一个应用"。页面删掉的那一刻，token CSS 五份拷贝的问题自动消解一半。

3. **把"诚实"还给界面**。欢迎语跟着角色走（打开就是大帅的问候），删掉"全程在你电脑上运行"这种已经不成立的宣言，本地引擎从开关降级为设置深处的一行状态。我每天打开它，看到的每一句话都应该是真的。

4. **设置面板做减法而不是加法**。90% 的时间我只需要改人设和语速，那这两样就该在最上面；API key、计费模式、采样率是"每年碰两次"的东西，收进"高级"折叠。角色动态只看一行 summary，想看时间线再展开。

5. **让每次改动只落笔一次**。`sync_pages.bat` 十秒钟把前端推进 APK；common.css/js 让主题改一处生效。以后我改任何东西，成本都是"改一次"，不是"改五处再记得 xcopy"。

6. **性能保持克制**。不做虚拟列表，不引框架。等真实卡了再优化，而且优先做"删除"而不是"机制"。

最终形态：**一个 3000 行左右的 chat.html（产品本体）+ 一个 1500 行的 server.py 路由装配 + 五个各司其职的后端模块 + 一条同步进 APK 的命令**。打开就是大帅在等你说话，设置里没有一句废话，仓库里没有一具尸体——这就是"比以前舒服太多"的样子。
